# Code Generation Mechanisms

Rust projects use three code generation mechanisms with distinct use cases: standalone Go tools for external schema-to-code generation, procedural macros for type system integration, and trait objects with dynamic loading for runtime plugin architectures. Each mechanism serves different needs with clear boundary conditions.

The first mechanism is presented through one worked option: standalone Go generator programs under `tools/internal/gen/`, writing generated crates under `pkg/rs/gen/`. That is the natural choice in a polyglot monorepo whose generators share schema-parsing code across several target languages. The same pattern — an external program that reads non-Rust schemas and writes committed Rust source — works with a Rust generator binary (an `xtask`-style workspace member) in a Rust-only repository; a `build.rs` script is the alternative when the output should not be committed. Substitute the paths accordingly.

## Core Concepts

- **Go tools for external schemas**: Standalone Go programs in `tools/internal/gen/rs/` parse non-Rust sources (JSON Schema, protobuf) and output Rust code to `pkg/rs/gen/{crate-name}/src/`. Tools use shared parsing utilities from `tools/internal/gen/common/` and language-specific templates. Generated crates are regular workspace members, committed to version control. CI freshness checks verify generated code stays in sync with schemas
- **Procedural macros for Rust types**: Derive macros use syn/quote workflow to generate code from Rust type definitions. Input is Rust AST (types with attributes), output is generated Rust code. Compiles during macro expansion phase. Type system integration (custom derives, attribute macros) but compile-time cost scales with macro complexity
- **Trait objects for plugins**: Dynamic loading via `libloading` with `dyn Trait` provides runtime extensibility. Plugins compiled as separate `cdylib` crates expose `#[no_mangle]` factory functions. Host loads via `libloading::Library` at runtime. ABI stability requires `abi_stable` crate or versioning discipline. Use when plugins discovered at runtime or developed independently

## Mechanism Comparison

| Aspect | Go Tools | Procedural Macros | Trait Objects |
|--------|----------|-------------------|---------------|
| **Input** | External files (JSON, proto) | Rust type definitions | Runtime-loaded libraries |
| **Output location** | `pkg/rs/gen/{crate-name}/src/` | Inline in crate | Separate compiled libraries |
| **Compile-time cost** | None (pre-generated) | Macro expansion time | None (runtime loading) |
| **Debuggability** | Committed, inspectable source files | Generated code in expansions | Standard debugging |
| **Use case** | Schema-first development | Type system extensions | Plugin architectures |

## Go Tools Pattern

### Generation Workflow

Go programs in `tools/internal/gen/rs/` follow a common pipeline: parse schema sources using shared utilities from `tools/internal/gen/common/`, extract a view model, render Rust code through templates, and write output to `pkg/rs/gen/{crate-name}/src/`.

```go
// tools/internal/gen/rs/types/main.go
package main

import (
    "tools/internal/gen/common/schema"
    "tools/internal/gen/rs/types/templates"
)

func main() {
    schema := schema.ParseDir("pkg/schemas/types/")
    viewModel := extractTypes(schema)
    templates.Render(viewModel, "pkg/rs/gen/types/src/lib.rs")
}
```

### Generated Output

```rust
// pkg/rs/gen/types/src/lib.rs
// Code generated by tools/internal/gen/rs/types. DO NOT EDIT.

use serde::{Deserialize, Serialize};

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct User {
    pub id: String,
    pub name: String,
    pub email: String,
}
```

### Using Generated Crates

Generated crates are regular workspace members. Handwritten crates depend on them through standard workspace path dependencies:

```toml
# pkg/rs/domain/user/Cargo.toml
[dependencies]
types = { path = "../../gen/types" }
```

```rust
// pkg/rs/domain/user/src/lib.rs
use types::User;
```

### Generated Code Immunity

Generated code requires immunity from manual editing:

- **VCS commitment**: Generated files are committed to version control, providing inspectable source and stable builds without requiring generation tools at compile time
- **DO NOT EDIT header**: Every generated file starts with `// Code generated by {tool}. DO NOT EDIT.`
- **CI freshness checks**: CI regenerates and diffs against committed files; drift fails the build

## Procedural Macro Pattern

### Derive Macro Structure

```rust
use proc_macro::TokenStream;
use quote::quote;
use syn::{parse_macro_input, DeriveInput};

#[proc_macro_derive(MyDerive)]
pub fn my_derive(input: TokenStream) -> TokenStream {
    let input = parse_macro_input!(input as DeriveInput);

    let name = &input.ident;

    let expanded = quote! {
        impl MyTrait for #name {
            fn my_method(&self) -> String {
                stringify!(#name).to_string()
            }
        }
    };

    TokenStream::from(expanded)
}
```

### Use Cases

- **Type system integration**: Custom derives extending type behavior (thiserror, serde, typed-builder)
- **Compile-time validation**: Macros verify constraints during compilation
- **Ergonomic APIs**: Reduce boilerplate for common patterns

### Boundaries

- **Use when**: Input is Rust type definitions, type system integration required, ergonomics justify compile-time cost
- **Avoid when**: Input sources are non-Rust (use Go tools), large schemas (>50 types), debugging complexity prohibitive

## Trait Object Plugin Pattern

### Plugin Contract

Shared crate defines trait:

```rust
// plugin-trait crate
pub trait Plugin: Send + Sync {
    fn name(&self) -> &str;
    fn execute(&self, input: &str) -> Result<String, Box<dyn std::error::Error>>;
}
```

### Plugin Implementation

```rust
// plugin-a crate
use plugin_trait::Plugin;

pub struct PluginA;

impl Plugin for PluginA {
    fn name(&self) -> &str {
        "plugin-a"
    }

    fn execute(&self, input: &str) -> Result<String, Box<dyn std::error::Error>> {
        Ok(format!("plugin-a processed: {}", input))
    }
}

#[no_mangle]
pub extern "C" fn create_plugin() -> Box<dyn Plugin> {
    Box::new(PluginA)
}
```

### Host Application

```rust
use libloading::{Library, Symbol};
use plugin_trait::Plugin;

struct PluginManager {
    plugins: Vec<(Library, Box<dyn Plugin>)>,
}

impl PluginManager {
    fn load(&mut self, path: &str) -> Result<(), Box<dyn std::error::Error>> {
        unsafe {
            let lib = Library::new(path)?;
            let create: Symbol<unsafe extern "C" fn() -> Box<dyn Plugin>> =
                lib.get(b"create_plugin")?;
            let plugin = create();
            self.plugins.push((lib, plugin));
        }
        Ok(())
    }
}
```

### ABI Stability

Rust has no stable ABI across compiler versions. Mitigations:

- **abi_stable crate**: Provides stable ABI types for production plugin systems with independent versioning
- **Synchronized compilation**: Monorepo with synchronized compiler versions for internal plugins
- **WASM alternative**: Sandbox and ABI stability with runtime overhead

Recommendation: use `abi_stable` for production open plugin ecosystems. Direct trait object loading viable for controlled environments with synchronized builds.

## Anti-Patterns

- **Procedural macros for external schemas**: Macro expansion expects Rust AST input. External files require parsing in macro, coupling phases. Solution: use Go tools for external schema compilation
- **Go tools for type-level generation**: Go generator tools cannot access Rust type information. Solution: use procedural macros for type-driven generation
- **Trait objects without ABI stability**: Plugins compiled with different compiler versions cause undefined behavior. Solution: use `abi_stable` or synchronize compiler versions
- **Generated code bypass**: Manually writing types in `pkg/rs/{group}/` that duplicate schema-defined types. Manual edits to `pkg/rs/gen/` vanish on regeneration. Solution: edit the source schemas and regenerate
